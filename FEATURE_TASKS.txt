ЗАЧЕМ
  Пользователь, всегда качающий MP3 в свою папку, перестаёт каждый запуск

  Вместо этого читать маленький JSON из binaries::data_dir() и сеять
  format/out_dir (и будущий quality) из него. Запись — через eframe `App::save`
  или по изменению с дебаунсом, но не в кадре ui().

ТОЧКИ РАСШИРЕНИЯ

СОБЛЮДЕНИЕ АРХИТЕКТУРЫ
  Использует уже существующий data_dir(); serde_json уже в зависимостях; движок
  не затрагивается, границы слоёв целы.

РИСКИ И ЛОВУШКИ
  Блокирующая ловушка: запись файла каждый кадр в ui() — нарушение горячего пути;
  сохранять только по изменению либо в App::save. Битый/отсутствующий файл обязан
  МОЛЧА откатываться к текущим дефолтам, а не ронять старт.

ЗАДАЧА 11: Очередь загрузок (пакет из нескольких ссылок)
################################################################################
Объём:            L
Приоритет:        крупная, отложенная
В планах README:  ДА («Одновременная загрузка нескольких файлов»)
Слои/файлы:       src/model.rs (Progress.download_id, Done/Failed несут id,
                  State::Queued),
                  src/engine/mod.rs (start/run принимают id, метят события),
                  src/app.rs (ограниченный queue: Vec, State, все match)

ЗАЧЕМ
  Пользователь ставит десяток ссылок в очередь и уходит — они качаются по одной
  без ручного перезапуска после каждой.

ЧТО СДЕЛАТЬ
  Завести в SavioApp ограниченное `queue: Vec<QueueItem>` (потолок в духе
  LOG_LIMIT) и состояние `State::Queued`. Чтобы развести события нескольких
  дочерних yt-dlp по одному каналу Event, добавить `download_id: u32` в Progress
  (он Copy — тип обязан остаться Copy) и нести id в Done/Failed, РАСШИРЯЯ варианты,
  а не заводя второй канал. engine::start получает id, run() (mod.rs) метит каждое
  событие.

ТОЧКИ РАСШИРЕНИЯ
  Progress (model.rs:114), Event Done/Failed (model.rs:140), enum State (app.rs
  ~25), engine::start + Handle (mod.rs:23,41), can_start()/start() (app.rs
  ~381/388), поле queue в SavioApp (~210).

СОБЛЮДЕНИЕ АРХИТЕКТУРЫ
  Единственный канал Event сохраняется, движок остаётся CLI-пригодным. State/Event
  расширяются, а не переосмысляются; очередь несёт предел памяти по Правилу 1.

РИСКИ И ЛОВУШКИ
  Смена Done(PathBuf) на структуру с id заденет ВСЕ исчерпывающие match — это и
  есть задуманная компилятором работа, но объёмная (по всему app.rs). Блокирующая
  ловушка: никаких join потоков на UI; каждая загрузка — свой поток; не плодить
  потоки без предела — запускать строго по одному из очереди.

ГОТОВНОСТЬ
  [ ] build / clippy / test
  [ ] версия: minor (заметная возможность)
  [ ] README: обновить (раздел «Использование», пункт планов вычеркнуть)
  [ ] CLAUDE.md: возможно правило про id-маршрутизацию событий одного канала
  [ ] UI: очередь пустая/в работе/с ошибкой отдельного элемента, отмена, 520×420

ТОЧКИ РАСШИРЕНИЯ

ЗАДАЧА 13: Паника wgpu при программном ресайзе окна   ⚠ дефект, не функционал
################################################################################
Объём:            S на воспроизведение и диагностику; M, если чинить самим
Приоритет:        низкий по частоте, высокий по последствиям
В планах README:  нет
Слои/файлы:       src/main.rs (NativeOptions/ViewportBuilder), Cargo.toml
                  (версия eframe), src/app.rs (maximize_pending).
                  В стеке падения кода Savio нет — виноват не наш слой.

ЗАЧЕМ
  Приложение падает целиком, теряя идущую загрузку, и в релизе падает МОЛЧА:
  консоль скрыта (`windows_subsystem = "windows"`, main.rs:2), поэтому текст
  паники пользователю не достаётся вообще — окно просто исчезает. Такое
  сообщение о проблеме нечем расследовать: ни журнала, ни кода возврата никто
  не увидит. Это ровно тот случай, ради которого заведено Правило 6: сборка,
  clippy и тесты здесь чисты, а функция ломается.

СИМПТОМ
  Обнаружено 2026-07-25 при глазном прогоне задачи 1 («Скопировать журнал»).
  Развёрнутому окну программно делается SW_RESTORE и сразу же MoveWindow с
  ВНЕШНИМ размером 520×420 — то есть клиентская часть 504×381, ниже заявленного
  в main.rs минимума 520×420. eframe отдаёт в wgpu поверхность (504, 32728):

      thread 'main' panicked at wgpu-29.0.4/src/backend/wgpu_core.rs:3879:
      wgpu error: Validation Error
        In Surface::configure
          `Surface` width and height must be within the maximum supported
          texture size. Requested was (504, 32728), maximum extent for either
          dimension is 8192.

  Ширина приходит верная, высота — мусор (32728 = 0x7FD8, похоже на переполнение
  знакового 16-битного значения). Проверено на чистом v0.4.0 из git stash:
  падает слово в слово, к кнопке копирования отношения не имеет.

  Мышью до этого не дотянуться: минимум окна Windows соблюдает при перетаскивании
  рамки. Нужен именно программный ресайз — а его делают не только тесты:
  оконные менеджеры (FancyZones и прочие PowerToys), удалённый рабочий стол,
  смена разрешения и отключение монитора двигают и меняют размер чужих окон сами.

ВОСПРОИЗВЕДЕНИЕ (Windows, PowerShell, отладочная сборка)
  cargo build && ./target/debug/savio.exe     # окно само разворачивается кадром
  # $h — HWND окна: (Get-Process savio).MainWindowHandle
  # user32: ShowWindow, MoveWindow через обычный Add-Type P/Invoke
  [W]::ShowWindow($h, 9)                            # SW_RESTORE
  Start-Sleep -Milliseconds 500
  [W]::MoveWindow($h, 100, 100, 520, 420, $true)    # ВНЕШНИЕ 520×420
  # процесс умирает с кодом 101

  Не падает при: SW_RESTORE, пауза 2 с, MoveWindow(120,120,536,459) — внешний
  размер, дающий клиент ровно 520×420.

ЧТО СДЕЛАТЬ
  1. Проверить на РЕЛИЗНОЙ сборке. Валидация wgpu не зависит от debug_assertions,
     так что «в релизе не падает» предполагать нельзя — только проверять, собрав
     с видимой консолью либо с записью паники в файл.
  2. Развести две переменные, которые в наблюдении смешаны: виноват сам размер
     ниже минимума — или гонка с ещё не законченным восстановлением окна?
     Прогнать порознь: (а) корректный размер сразу после SW_RESTORE без паузы,
     (б) размер ниже минимума с паузой в 2 с.
  3. Посмотреть, причастен ли наш собственный разворот окна: `maximize_pending`
     (app.rs) шлёт ViewportCommand::Maximized(true) первым кадром, и repro
     стартует именно из этого программно развёрнутого состояния. Проверить,
     воспроизводится ли на окне, развёрнутом пользователем вручную.
  4. По итогу — либо сообщение вверх по течению (eframe/winit/wgpu) с этим
     воспроизведением, либо обход у нас. Обход искать в main.rs; смена рендерера
     на glow — крайняя мера, см. риски.

ТОЧКИ РАСШИРЕНИЯ
  NativeOptions/ViewportBuilder (main.rs:12), maximize_pending (app.rs ~262
  и его отправка в ui() ~612), версия eframe (Cargo.toml).

СОБЛЮДЕНИЕ АРХИТЕКТУРЫ

ЗАДАЧА 18: Монитор производительности и игровой оверлей
################################################################################
Объём:            L, и это две разные задачи: монитор и оверлей
Приоритет:        зависит от решения по задаче 17
В планах README:  нет
Слои/файлы:       новый src/engine/monitor.rs (опрос),
                  src/model.rs (Event:344), src/app.rs (Tab:86, tab_bar:788),
                  src/main.rs (второй вьюпорт под оверлей)

ЗАЧЕМ
  Пользователь видит загрузку CPU, GPU, памяти, дисков и сети в реальном
  времени, список процессов по потреблению — и то же самое поверх игры, не
  сворачивая её.

  Оговорка из задачи 17 действует и здесь: это не про скачивание. Оверлей
  вдобавок — самостоятельный продукт (MSI Afterburner, RTSS), а не вкладка.

ЧТО СДЕЛАТЬ
  Поток-опросчик с интервалом около секунды, свой приёмник Event (как у
  вкладки «Метаданные»), готовые строки собираются при получении данных, а не
  в кадре: список процессов — это сотни строк, и format! по ним 60 раз в
  секунду недопустим (Правило 1). Кадры просить через request_repaint_after:
  без ввода egui окно не перерисовывает.
  Оверлей — отдельный вьюпорт egui (show_viewport_deferred с ViewportBuilder:
  without decorations, transparent, always on top, mouse passthrough), а не
  второе приложение и не второй процесс.

ТОЧКИ РАСШИРЕНИЯ
  Tab (app.rs:86), tab_bar (app.rs:798) — см. задачу 17, деление на 2;
  MetaPanel (app.rs:96) — образец панели со своим каналом и drain;
  start_metadata (mod.rs:271) — образец фоновой задачи.

СОБЛЮДЕНИЕ АРХИТЕКТУРЫ
  Канал остаётся единственной связью движка с UI. Опрос железа — та же новая
  строка в таблице слоёв, что и в задаче 17: делать обе имеет смысл на одном
  сборщике, иначе появятся два разных способа спросить загрузку процессора.

РИСКИ И ЛОВУШКИ
  - Любой накопитель ограничен по размеру — это уже правило (LOG_LIMIT).
    История для графиков обязана быть кольцевым буфером фиксированной длины,
    иначе оставленный на ночь монитор съест память.
  - Сейчас Savio в покое не тратит ни кадра. Секундный опрос означает
    постоянную перерисовку, в том числе у свёрнутого окна. Нужен явный
    останов опроса, когда вкладка не видна и оверлей выключен, — иначе
    загрузчик начнёт греть ноутбук в фоне.
  - FPS чужого приложения со стороны не измеряется. Нужен перехват Present
    (PresentMon, ETW), на Windows — с правами администратора. Пункт «FPS
    (если доступно)» либо вычеркнуть, либо выносить в отдельную задачу: иначе
    он утащит за собой всю остальную работу.
  - Оверлей поверх игры виден только в оконном и безрамочном режимах. В
    эксклюзивном полноэкранном обычное окно не показывается никогда — туда
    рисуют только перехватом графического API. Сказать это в UI обязательно,
    иначе «оверлей не работает» станет главным отзывом, и справедливо.
  - Потребление на процесс: CPU, память и диск даёт sysinfo; GPU на Windows —
    только счётчики «GPU Engine» через PDH; сеть на процесс кроссплатформенно
    не даётся вовсе (нужен ETW). Колонка, пустая на половине систем, — тот же
    молчаливый провал, что и «Температура: —».
  - Прозрачное окно и wgpu: дефект 13 показывает, что геометрия окна в текущей
    связке уже роняет приложение целиком. Второй вьюпорт — новая площадь для
    того же класса падений, и падение оверлея убьёт идущую загрузку.

ЗАДАЧА 19: Управление режимами питания и производительности
################################################################################
Объём:            L
Приоритет:        низкий: реалистичная часть здесь мала, см. ловушки
В планах README:  нет
Слои/файлы:       src/engine/power.rs (чтение и применение режима),
                  src/model.rs (Event:344), src/app.rs (вкладка из задачи 18)

ЗАЧЕМ
  Пользователь переключает режим питания и профили производительности прямо из
  Savio, не открывая параметры Windows.

ЧТО СДЕЛАТЬ
  Показать текущий режим питания и дать его переключать. Всё остальное из
  постановки — профили CPU и GPU, режим вентиляторов, параметры накопителей —
  сначала проверить на достижимость, см. ловушки: реалистичной остаётся, судя
  по всему, только схема питания.

ТОЧКИ РАСШИРЕНИЯ
  Вкладка монитора из задачи 18; Event (model.rs:344) — сообщение о
  применённом режиме; start_metadata (mod.rs:271) — образец фоновой задачи
  (переключение схемы уходит в поток, в ui() запускать процессы нельзя).

СОБЛЮДЕНИЕ АРХИТЕКТУРЫ
  Через powercfg это обёртка над внешней программой — ровно то, что Savio уже
  умеет, и слои не ломаются. Через powrprof.dll это первый в проекте вызов
  системного API напрямую: понадобится либо windows-crate, либо ручные extern.

РИСКИ И ЛОВУШКИ
  - Проверено вживую (Windows 11, обычные права, 2026-07-26):
    `powercfg /getactivescheme` и `/list` читаются без администратора, но
    показывают три классические схемы — Balanced, High performance, Power
    saver. Режимов из постановки («Best Performance», «Battery Saver») среди
    них нет вовсе: в Windows 11 ползунок «Режим питания» переключает не схему,
    а overlay-схему, и powercfg о ней не знает — `/overlaylist` отвечает
    «Invalid Parameters». Добраться до неё можно только недокументированными
    PowerGetEffectiveOverlayScheme / PowerSetActiveOverlayScheme из
    powrprof.dll. Показать вместо ожидаемых названий три powercfg-схемы —
    значит показать список, которого пользователь в своей системе не видел.
  - «Применять сразу и не спрашивать» разумно для схемы питания и опасно для
    оборотов вентилятора: там неверное значение кончается перегревом. Savio
    уже переспрашивает перед необратимым (модалка очистки метаданных) — та же
    мера нужна всему, что трогает охлаждение.
  - Вентиляторы и профили CPU/GPU идут через EC и вендорские SDK (NVAPI, ADL,
    драйверы конкретных ноутбуков): права администратора, свой драйвер, разное
    поведение на каждой модели. Трезвая оценка — не делать вовсе.
  - Кроссплатформенность: аналога powercfg на Linux и macOS нет, cpufreq/TLP и
    pmset — другие сущности с другим смыслом. Вкладка выйдет Windows-only, а
    Правило 2 требует пары к каждой ветке #[cfg]. Нужна честная заглушка «на
    этой системе недоступно».
  - «Отображать только поддерживаемое» проверяется попыткой, а не наличием
    API: функция может существовать, вернуть успех и ничего не изменить
    (Правило 6). После применения — перечитать текущий режим и сверить с
    запрошенным, иначе переключатель будет врать.
